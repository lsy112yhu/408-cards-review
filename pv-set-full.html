方法论 · 三类约束模型与解题四步

一切 PV 题的约束，拆到底只有三类。先认出约束属于哪一类，信号量的初值和用法就定了一半。

第 1 类：互斥 —— 一个东西，同一时刻只能一个人用

例子：唯一出入口、一把铁锹、某个共享变量、对缓冲区的修改。设一个互斥信号量，初值 1，用法是把临界区紧紧夹在 P、V 之间：

P(mutex);
临界区;
V(mutex);

第 2 类：资源数量限制 —— 最多允许 N 个进程同时做某件事

例子：博物馆最多 N 人、N 个座位、N 个空位。设一个计数信号量，初值 N：做这件事前 P 一下（占一个名额），做完 V 一下（还名额）。名额用完，后来者睡在 P 上。

semaphore resource = N;

第 3 类：同步 —— A 做完以后，B 才能做

设一个同步信号量，初值 0：做 A 的进程在 A 之后 V 一下（宣布「条件成立」），做 B 的进程在 B 之前 P 一下（等条件成立）。初值 0 意味着一开始条件不成立，B 必须等。

进程甲: 操作A; V(sync);
进程乙: P(sync); 操作B;

P、V 的本质。P 操作是「我要满足这个条件 / 拿到这个资源」，V 操作是「我让这个条件成立 / 把资源还回去」。写代码时每写一个 P，先问自己：我在等什么条件、拿什么资源；每写一个 V，问：我让哪个条件成立了。

解题四步

① 拆约束：把题面逐句过一遍，每句问三个问题——谁和谁互斥？谁必须等谁先做完？哪种资源只有几个？列成清单，一条不落。
② 定信号量：先识别全部约束，再判断哪些约束可以共用一个信号量（例如同一资源的「计数」与基于它的准入限制，往往一个计数信号量就能兼管），最后定信号量的数量与初值，写清各自的名称、初值、管什么。互斥量初值 1，同步量初值 0，计数类初值等于资源总数（注意初始存量：箱子里已有货时，计数要按已有量起算）。
③ 写代码：同步的 P 放在互斥的 P 之前（可能睡着的等待不要抱着锁睡）——这条次序是生产者–消费者一类有界缓冲区模板的安全次序，不是普遍铁律；通用原则是：不要持锁等待一个只能由被你挡住的进程满足的条件。互斥的 P、V 紧夹临界区，不多包一行、不少包一行。
④ 查：查 P 的顺序（持锁等待是死锁的温床）、查每个 V 有没有对应的 P、查信号量初值与题目初始状态对不对得上、挑最危险的交错顺序走查一遍。

板书对照。讲义课件在第 3 类里把信号量名也顺手写成了 mutex（初值 0）——名字是顺手沿用的，看初值就知道它是同步量。信号量的名字不重要，初值和 P、V 的位置才重要；正文一律按语义命名（同步量取 sync、full、dug 这类名字），与课件只有命名之别。

一、生产者–消费者问题（模板题）

题目。一组生产者进程和一组消费者进程共享一个初始为空、大小为 n 的缓冲区。缓冲区不满时，生产者才能把消息放入缓冲区，否则必须阻塞；缓冲区不空时，消费者才能从缓冲区中取出消息，否则必须等待；并且缓冲区是临界资源，必须互斥访问。用信号量机制实现两组进程的同步与互斥。

分析：拆约束

互斥，一条：缓冲区是临界资源，同一时刻只许一个进程动它（放入和取出都是改缓冲区状态）——配互斥量 mutex。
同步，两条：其一，「有空位」是生产者能放的前提，空位的有无取决于消费者取没取——这是状态同步，配计数信号量 empty 记空位个数；其二，「有产品」是消费者能取的前提，取决于生产者放没放——配计数信号量 full 记产品个数。
注意 empty、full 管的不是「防同时访问」，而是「系统当前状态允不允许你继续」：它们本质是带计数的状态开关。这也是它俩初值一个 n、一个 0 的原因——初始缓冲区空，空位 n 个、产品 0 个。

信号量设计

名称初值管什么
emptyn缓冲区中的空位数（计数/同步）：生产者放前 P，消费者取后 V
full0缓冲区中的产品数（计数/同步）：消费者取前 P，生产者放后 V
mutex1缓冲区互斥访问：放、取动作本身互斥

代码

semaphore empty = n; // 空位数
semaphore full = 0; // 产品数，初始缓冲区为空
semaphore mutex = 1; // 缓冲区互斥锁

producer() {
while (1) {
生产一个产品;
P(empty); // 先等空位：可能睡着的等待放在进临界区之前
P(mutex); // 再上锁
把产品放入缓冲区;
V(mutex); // 放完立刻解锁
V(full); // 产品数 +1，唤醒等产品的消费者
}
}

consumer() {
while (1) {
P(full); // 先等产品
P(mutex); // 再上锁
从缓冲区取一个产品;
V(mutex);
V(empty); // 空位数 +1，唤醒等空位的生产者
消费该产品;
}
}

验算走查

走查一（反序为什么死锁）。设生产者把顺序写反：先 P(mutex) 再 P(empty)。取 n = 1、缓冲区已满（empty = 0）这一刻：生产者 P(mutex) 成功，抱着锁去 P(empty)，empty = 0，睡着——锁还在它手里。消费者想取产品腾空位，必须先 P(mutex)，锁被占，睡着。两人互相等对方先动：生产者等空位，空位要靠消费者取；消费者等锁，锁在生产者手里。死锁。正序时生产者睡在 P(empty) 上，手里没有锁，消费者能正常取、V(empty) 把它叫醒——所以「可能导致阻塞的条件等待，放在进入临界区之前」是铁律。

走查二（满边界）。n = 2，生产者连放两个：empty 2 → 1 → 0。第三次 P(empty) 睡下（不持锁）。消费者取走一个，V(empty) 使 empty = 1 并唤醒生产者，生产者这才 P(mutex) 放入。缓冲区产品数始终在 0～2 之间，不溢出、不下溢（下溢由 full 同理守住：空时消费者睡在 P(full) 上）。

易错点

① P 的顺序反了。同步 P（P(empty)/P(full)）必须在互斥 P(mutex) 之前，反序且缓冲区满/空时就是上面的持锁死等。② 把 empty、full 当锁用。它俩是状态计数，不是互斥量；省掉 mutex，两个生产者仍可能同时改缓冲区。V 的两个 V 顺序则无所谓，V(mutex) 与 V(full) 谁先谁后都对——要紧的只有 P 的顺序。

二、奇偶分拣的生产者–消费者 综合题 · 7 分

题目。三个进程 P1、P2、P3 互斥使用一个包含 N（N > 0）个单元的缓冲区。P1 每次用 produce() 生成一个正整数并用 put() 送入缓冲区某一空单元中；P2 每次用 getodd() 从该缓冲区中取出一个奇数并用 countodd() 统计奇数个数；P3 每次用 geteven() 从该缓冲区中取出一个偶数并用 counteven() 统计偶数个数。请用信号量机制实现这三个进程的同步与互斥活动，并说明所定义信号量的含义（要求用伪代码描述）。

分析：拆约束

互斥，一条：三个进程都要动缓冲区，任意两者不能同时动——mutex = 1，与模板相同。
资源计数，一条：空单元只有 N 个，P1 放之前必须确认有空位——empty = N，与模板相同。
同步，本题的难点：消费者不是一个而是两个，且各取所需——P2 只许取奇数，P3 只许取偶数。若照模板只设一个 full 记产品总数，会出这样的事：缓冲区里只有一个偶数时 full = 1，P2 先被调度，P(full) 成功，进缓冲区却发现没有奇数可取——取错不行、空手而归则 full 的计数已经被它消耗，语义全乱。所以「有产品」这个条件必须按奇偶拆成两个：odd 记缓冲区中奇数的个数，even 记偶数的个数，P2 只等 odd，P3 只等 even；P1 放完后按所放数的奇偶，只 V 对应的那一个。这样每个消费者被唤醒时，缓冲区里必有它要的那一类数。
建模前提要点明：本题默认缓冲区可以按奇偶挑取（题面说 P1 把数送入「某一空单元」，getodd()「从缓冲区中取出一个奇数」，都是挑取语义）。若缓冲区只能从队头取出、且不能暂存或重排（严格 FIFO），队头是偶数时 P2 连看都没法看，当前这套挑取方案就不能直接应用——考试按挑取模型答即可，但分析里把前提写出来，是这道题的得分眼。

信号量设计

名称初值管什么
emptyN空单元数：P1 放前 P，P2/P3 取走后 V
odd0缓冲区中奇数的个数：P2 取前 P，P1 放入奇数后 V
even0缓冲区中偶数的个数：P3 取前 P，P1 放入偶数后 V
mutex1缓冲区互斥访问

代码

semaphore empty = N; // 空单元数
semaphore odd = 0; // 缓冲区中奇数个数
semaphore even = 0; // 缓冲区中偶数个数
semaphore mutex = 1;

P1() {
while (1) {
int x = produce();
P(empty); // 等空单元
P(mutex);
put(x); // 放入某一空单元
V(mutex);
if (x % 2 == 1) V(odd); // 按奇偶只唤醒对应消费者
else V(even);
}
}

P2() {
while (1) {
int x;
P(odd); // 等奇数：被唤醒时必有奇数可取
P(mutex);
x = getodd(); // 取走一个奇数
V(mutex);
V(empty); // 归还一个空单元
countodd();
}
}

P3() {
while (1) {
int x;
P(even); // 等偶数
P(mutex);
x = geteven();
V(mutex);
V(empty);
counteven();
}
}

验算走查

走查（N = 1 的极限交错）。P1 生成奇数 3：P(empty) 后 empty = 0，放入，V(odd) 使 odd = 1。此刻 P3 在 P(even) 上睡（even = 0），不受影响；P2 被唤醒，取走 3，V(empty)。P1 再生成偶数 4：放入，V(even)；这次睡的是 P2，醒的是 P3。再看最危险的一种：P2、P3 同时在等，P1 放入偶数——只有 even 被 V，P3 醒、P2 继续睡，不存在「叫错人」。被唤醒的消费者进临界区后要取的那一类数一定还在：从 V(odd) 到 P2 取走之间，唯一能减少奇数个数的只有 P2 自己（P3 只取偶数、P1 只增不减），所以奇数不会被人捷足先登。此方案经交错探索验算（N = 3，P1 依次产 1～6，P2、P3 各取 3 个）：1117 个可达状态中无「取错类」、无溢出、无死锁。

易错点

① 只设一个 full。这是本题最常见的错法，后果见分析：消费者被唤醒却取不到自己那类数。② 消费者忘了 V(empty)。P2/P3 取走数后不归还空位，P1 放满 N 个后永久睡死。另注意 P1 的 V(odd)/V(even) 必须按刚放入那个数的奇偶来选，写反了两个计数会与实际库存脱节。

板书对照。讲义对本题只讲到思路（互斥一个量、奇偶两条消费路径各一个量、再加一个管空位的量），未给出完整代码；旁白转述的信号量名（for_odd、empty 一类）与正文命名（odd、even、empty）只是名字不同，方案与板书思路一致，无实质出入。

三、银行取号机 综合题 · 8 分

题目。某银行提供 1 个服务窗口和 10 个供顾客等待的座位。顾客到达银行时，若有空座位，则到取号机上领取一个号，等待叫号。取号机每次仅允许一位顾客使用。当营业员空闲时，通过叫号选取一位顾客，并为其服务。顾客和营业员的活动过程描述如下：

cobegin
{
process 顾客 i
{
从取号机获取一个号码；
等待叫号；
获取服务；
}
process 营业员
{
while (TRUE)
{
叫号；
为客户服务；
}
}
}
coend

请添加必要的信号量和 P、V（或 wait()、signal()）操作，实现上述过程中的互斥与同步。要求写出完整的过程，说明信号量的含义并赋初值。

分析：拆约束

资源计数，一条：座位只有 10 个，没座位的人连号都取不成（题面：「若有空座位，则到取号机上领取一个号」）——seat = 10，顾客进门先 P(seat) 占座，被叫到离座时 V(seat)。
互斥，一条：取号机每次仅允许一位顾客使用——mutex = 1，只夹住取号这一个动作。
同步，两条，正是板书上画的两条链：其一，「顾客取号 → 营业员叫号」：没有顾客取号，营业员不许空叫；有几位顾客在等，营业员心里要有数——waiting = 0，记已取号待叫的顾客数，顾客取号后 V(waiting)，营业员叫号前 P(waiting)。其二，「营业员叫号 → 顾客被服务」：顾客取了号不能自己跑去窗口，必须等叫到——service = 0，营业员叫号时 V(service)，顾客取号后 P(service) 等叫。两条链一环扣一环：waiting 管「营业员等顾客」，service 管「顾客等营业员」，方向相反，不要合并成一个。

信号量设计

名称初值管什么
seat10空座位数（资源计数）：顾客占座时 P，离座时 V
mutex1取号机互斥使用
waiting0已取号、等待叫号的顾客数（同步链一）：顾客取号后 V，营业员叫号前 P
service0叫号通知（同步链二）：营业员叫号时 V，顾客等号时 P

代码

semaphore seat = 10; // 空座位数
semaphore mutex = 1; // 取号机互斥
semaphore waiting = 0; // 已取号待叫的顾客数
semaphore service = 0; // 叫号通知

process 顾客 i {
P(seat); // 有空座位才能进
P(mutex); // 取号机一次一人
从取号机获取一个号码;
V(mutex);
V(waiting); // 通知营业员：又一位顾客在等
P(service); // 等待叫号，没叫到就睡在这里
V(seat); // 被叫到，离开座位，座位让给门外的人
获取服务; // 与营业员的「为客户服务」是同一段服务过程的两面
}

process 营业员 {
while (TRUE) {
P(waiting); // 无人等待时睡下，不空叫
叫号; // 选取一位等待中的顾客
V(service); // 发出一个不区分具体号码的服务通知
为客户服务;
}
}

验算走查

走查一（第 11 位顾客）。10 个座位坐满时 seat = 0，第 11 位顾客睡在 P(seat) 上——注意此时他还没取号，waiting 不增，营业员不会为他叫号。营业员叫走一位：那位顾客 P(service) 通过后 V(seat)，seat = 1，第 11 位顾客这才被唤醒去取号。若把 V(seat) 错放在取号之后，座位在顾客整个等待+服务期间被白占，第 11 人要干等到前一位服务结束才进得来，与「座位是供等待用的」题意不合。

走查二（叫号会不会丢）。顾客执行完 V(waiting) 后、还没执行到 P(service) 就被调度走；营业员被唤醒，叫号并 V(service)，service = 1，然后开始服务。顾客回来执行 P(service)：service = 1，直接通过，不会错过这次叫号——计数信号量把「事件发生过」记在数值里，不是一次性开关，同理 waiting 的计数也不会丢人。此方案经交错探索验算（座位缩比为 2、3 位顾客）：无超员、无「未叫号先被服务」、无死锁。

走查三（语义限定：叫到的号，对得上人吗）。要说清这套方案到底保证了什么：公共的 service 只是一个不记名的计数，它保证的是「有顾客在等」与「营业员叫号」之间的服务同步——有人等，营业员才叫；叫了号，才有一位顾客被放行去接受服务。它不保证被唤醒的那位顾客就是被叫号码本人。举一例：顾客 A 取了 1 号，还没执行到 P(service) 就被切换走；顾客 B 取 2 号后先在 P(service) 上阻塞；营业员叫 1 号、执行 V(service)，被唤醒的完全可能是先睡下的 B——B 拿着 2 号先被服务，A 随后被下一次叫号放行。严格地说，这便不算「按指定号码服务」——叫的是 1 号、被放行的却可能是 2 号。但 408 常见参考解用的正是这个抽象简化模型：号码只用于建模「等待人数」，不做按号点名；正文将它作为统考常用简化方案，不声称具备号码身份匹配能力。真要严格按号唤醒，就得给每个号码（或每位顾客）配一个专属信号量、用数组按号码索引——那已超出本题的过程描述要求，这里只点明边界，不展开。

易错点

① 只设 service 不设 waiting。营业员不等顾客到来就一轮轮空叫，service 被攒出一堆计数，后来的顾客 P(service) 不等真叫号直接通过，同步链断裂。② P(seat) 与取号的顺序。必须先有座再取号，与题面措辞对应；若先取号后占座，没座位的人也占了一个号，waiting 与真实等待人数脱节。

板书对照。讲义板书只画了两条同步链（顾客取号 → 营业员叫号；营业员叫号 → 顾客被服务）与双方动作拆解，未给出信号量定义和代码。正文按这两条链落实为 waiting 与 service 两个同步量——其中 service 即讲义旁白提到的那个 service 信号量；思路无出入，属按板书框架补全。

四、信箱辩论（双向生产者–消费者） 综合题 · 9 分

题目。有 A、B 两人通过信箱进行辩论，每个人都从自己的信箱中取得对方的问题。将答案和向对方提出的新问题组成一个邮件放入对方的邮箱中。假设 A 的信箱最多放 M 个邮件，B 的信箱最多放 N 个邮件。初始时 A 的信箱中有 x 个邮件（0 < x < M），B 的信箱中有 y 个邮件（0 < y < N）。辩论者每取出一个邮件，邮件数减 1。A 和 B 两人的操作过程描述如下：

CoBegin
A {
while (TRUE) {
从 A 的信箱中取出一个邮件；
回答问题并提出一个新问题；
将新邮件放入 B 的信箱；
}
}
B {
while (TRUE) {
从 B 的信箱中取出一个邮件；
回答问题并提出一个新问题；
将新邮件放入 A 的信箱；
}
}
CoEnd

当信箱不为空时，辩论者才能从信箱中取邮件，否则需要等待。当信箱不满时，辩论者才能将新邮件放入信箱，否则需要等待。请添加必要的信号量和 P、V（或 wait、signal）操作，以实现上述过程的同步。要求写出完整过程，并说明信号量的含义和初值。

分析：拆约束

先认清模型：这是两个方向的生产者–消费者叠在一起。看 A 的信箱：往里放的是 B，从里取的是 A——对 A 箱而言 B 是生产者、A 是消费者；看 B 的信箱则正好反过来。每个人同时是「自家箱子的消费者 + 对方箱子的生产者」。
于是每个信箱独立配一套模板三件套：记存量的 full、记空位的 empty、护箱子的 mutex。两套之间不共享任何信号量——这是本题能成立的关键（死锁分析见走查）。
初值必须按初始存量起算，这是本题与模板题唯一的大不同：A 箱已有 x 封信，所以 fullA = x（A 开局就有 x 封可取）、emptyA = M − x（只剩 M − x 个空位，B 最多再放这么多）；B 箱同理 fullB = y、emptyB = N − y。若顺手按「初始为空」写 full = 0、empty = M，A 开局 P(fullA) 就睡死、B 还能往已有 x 封的箱子里超放 M 封，两头全错。

信号量设计

名称初值管什么
fullAxA 箱中现有邮件数：A 取前 P，B 放后 V
emptyAM − xA 箱空位数：B 放前 P，A 取后 V
mutexA1A 箱互斥访问（A 取、B 放不能同时动 A 箱）

emptyBN − yB 箱空位数：A 放前 P，B 取后 V

semaphore fullB = y, emptyB = N - y, mutexB = 1; // B 箱三件套

P(fullA); // 等自家箱里有信
P(mutexA);

V(mutexA);
V(emptyA); // A 箱腾出一个空位

P(emptyB); // 等对方箱里有空位
P(mutexB);
将新邮件放入 B 的信箱;
V(mutexB);

}
}

P(mutexB);

V(mutexB);
V(emptyB);

P(emptyA);
P(mutexA);

V(mutexA);
V(fullA);

验算走查

走查一（双向同时进行会不会对锁死锁）。某一刻 A、B 同时开工：A 拿 mutexA 取自家信，B 拿 mutexB 取自家信——两把不同的锁，可真并发。取完后 A 想要 mutexB 放信、B 想要 mutexA 放信，看似交叉，但注意此刻两人手里都没有锁：取信段一结束，mutexA、mutexB 都已经 V 掉，放信段是「先等空位、再拿对方的锁」。死锁的必要条件之一是「持有并等待」，这里没人持有任何锁去等另一把锁，环就结不起来。两人顶多在同一把锁上排队，先到者放完 V 掉，后到者继续。这是死锁证明的第①段：双方都先释放本箱的锁、才去申请对方箱的锁，任何时刻都不存在交叉持锁。

走查二（死锁证明·余下两种等待）。先把守恒式写对：邮件总数不能只数两只箱子——A 箱存量 ＋ B 箱存量 ＋ A 处理中（已取未放）＋ B 处理中 ＝ x ＋ y，恒定不变（每人每轮取一封、放一封，邮件只在「箱中 / 手中」之间搬家）。写成「两箱之和恒为 x ＋ y」是错的：有人正拿着一封作答时，那封不在任何箱里，两箱之和会暂时少于 x ＋ y。
第②段，空位等待不可能同卡：设 A、B 都卡在等对方箱空位（A 卡 P(emptyB)、B 卡 P(emptyA)）。但走到这一步的前提，是两人的本轮都已先从自己箱里取走了一封——A 取信时 V(emptyA) 已给 A 箱腾出一个空位，B 取信时 V(emptyB) 已给 B 箱腾出一个空位。也就是说此刻两箱各至少有一个空位，与「两人都等不到空位」直接矛盾。所以空位等待不可能两人同卡，至少一方能把信放进去、链条滚动。
第③段，邮件等待不可能同卡：设 A、B 都卡在等自己箱有信（A 卡 P(fullA)、B 卡 P(fullB)）。卡在取信步意味着两人手里都没有处理中的邮件（处理中 ＝ 0），由守恒式，两箱之和恰为 x ＋ y；题面给定 0 < x、0 < y，故 x ＋ y > 0，两箱不可能同时为空，至少一箱有信、那一方不会被卡。
三段合起来：互斥锁不交叉持有、空位等待不可能同卡、邮件等待不可能同卡，死锁无从形成。此方案经交错探索验算（M = N = 2，x = y = 1）：含处理中的守恒式在所有可达状态成立、无越界、无死锁。

易错点

① 初值忘了初始存量。full 按 0、empty 按容量写是本题头号错误，见分析。② 两箱共用一个 mutex。只共用一把锁本身还不至于死锁（取、放都是短临界区），但若顺势把代码写成「取信时拿着锁去等对方空位」，立刻变成持锁等待、双向对死。分箱分锁、取放分段，是这道题的安全写法。

五、读者–写者问题（模型题）

题目。有读者和写者两组并发进程，共享一个文件。当两个或以上的读进程同时访问共享数据时不会产生副作用，但若某个写进程和其他进程（读进程或写进程）同时访问共享数据时，则可能导致数据不一致。因此要求：① 允许多个读者同时读；② 只允许一个写者写；③ 任一写者在写之前不允许其他读者或写者工作；④ 写者写之前，应让已有的读者和写者全部退出。

分析：拆约束

这道题的重点不再是「有没有互斥」，而是「谁和谁互斥」——一张非对称关系表：

读者写者
读者可以并发互斥
写者互斥互斥

难点在读者这一格：读者之间不许互斥（否则退化成大锁、丢了并发），但读者作为一个整体又必须与写者互斥。办法是把所有读者看作一个整体：用整型变量 count 记当前读者数；整体与写者之间用一把 rw 锁——第一个读者负责 P(rw) 把写者挡在门外，中间来的读者直接进（count 不为 0 说明门已经锁好），最后一个读者负责 V(rw) 把写者放进来。写者则简单：独占 rw。
但 count 本身是新引入的共享变量：读者们并发地 count++、count--，对 count 而言每个读者都是「写者」，写者之间必须互斥——所以还要一把 mutex 专护 count。注意区分：count 是普通整型变量（可以 ++、--），不是信号量；它在本题与哲学家方法 1 里的信号量 count 同名不同物，不要混。

正解一：读者优先版

名称初值管什么
rw1「读者整体」与写者之间的互斥（门锁）
mutex1保护整型变量 count 的互斥访问
count（整型变量）0当前正在读的读者数
semaphore rw = 1; // 读者整体与写者的互斥
semaphore mutex = 1; // 保护 count
int count = 0; // 当前读者数（普通变量，不是信号量）

reader() {
while (1) {
P(mutex);
if (count == 0) P(rw); // 我是第一个读者：锁门，挡住写者
count++;
V(mutex);
读操作; // 读者之间真并发，谁也不等谁
P(mutex);
count--;
if (count == 0) V(rw); // 我是最后一个读者：开门，放写者进
V(mutex);
}
}

writer() {
while (1) {
P(rw); // 独占：门外等所有读者退出
写操作;
V(rw);
}
}

验算走查（读者优先版）

「第一个锁门、最后一个开门」走查。R1 到：count 0 → 1，P(rw) 锁门，进读。R2 到：count 1 → 2，不碰 rw，直接进读——与 R1 并发，符合要求。W 到：P(rw) 被挡，睡。R1 退：count 2 → 1，不开门。R3 此刻新到：count 1 → 2，直接进读——它排在了 W 的前面插队。R2、R3 先后退完，count 到 0，V(rw)，W 才进。这条走查同时暴露了读者优先版的毛病：只要读者源源不断地来，W 理论上可以永远等下去（写者饥饿）——这正是下面公平版要解决的问题。

反例：没有 mutex 保护 count 的中间版（不要这样写）

reader() { // 反例：count 的判断与自增不原子
while (1) {
if (count == 0) P(rw);
count++;
读操作;
count--;
if (count == 0) V(rw);
}
}

竞态就藏在头两行。设 R1、R2 几乎同时到达：两人都读到 count == 0，都去 P(rw)——一个成功、一个睡在 rw 上（这还算运气好）；更糟的是自增丢更新：两人都执行 count++，count 本该是 2，实际只加成 1。随后先读完的那个读者 count-- 使 count 归 0，执行 V(rw) 把写者放了进来，而另一个读者还在读——写读并发，数据不一致，正是题目要防的事。教训：凡是「先判断计数、再按结果决定抢不抢锁」的结构，判断+计数这一段本身就是临界区，必须用 mutex 原子化。此中间版只作反例，不作正解。

正解二：公平版（加闸门 w，写者不再饥饿）

在读者优先版之上只加一个信号量 w = 1，充当一道先来后到的闸门：读者和写者在进入之前都要先过这道闸。关键在于占闸的时长不对称——读者只在「登记」的一瞬间占闸（登记完立刻 V(w)，然后去读），写者则全程占闸（从 P(w) 一直占到写完 V(w)）。先把公平性的前提说在前面：w 能保证写者不被后来读者无限插队，是在信号量等待队列为 FIFO 等公平唤醒、且已进入的读者能正常退出的前提下才成立的——若唤醒顺序任意（比如总是挑最新到达者），闸门排出的先后就落不了地，下面的走查默认这一前提。

semaphore w = 1; // 公平闸门，其余信号量同读者优先版

reader() {
while (1) {
P(w); // 先过闸排队
P(mutex);
if (count == 0) P(rw);
count++;
V(mutex);
V(w); // 登记完立刻放闸，不占着闸读
读操作;
P(mutex);
count--;
if (count == 0) V(rw);
V(mutex);
}
}

writer() {
while (1) {
P(w); // 过闸：一旦先拿到闸，后来的读者全卡在闸外
P(rw);
写操作;
V(rw);
V(w); // 写完才放闸
}
}

验算走查（公平版）

写者为什么不再饥饿。接上面走查的局面：R1 在读，W 到达。W 先 P(w) 拿下闸门，再 P(rw) 等 R1 退出（此时 count = 1，rw 在 R1 手里）。R2 新到：第一步 P(w) 就被挡住——它不能再像读者优先版那样绕过 W 直接登记。此后能读的只剩已经在读的 R1（有限个），R1 退完 count 归 0、V(rw)，W 立刻进入写。W 写完 V(rw)、V(w)，R2 才过闸登记。一句话：w 在公平排队前提下限制后来者插队，新读者只能排在已到达的写者之后。严格说这版是「写者不被无限插队」的公平版，并非写者绝对优先（已在读的读者仍先于写者读完）——这也是它叫「公平版」而不叫「写者优先」的原因。

易错点

① 公平版里 V(w) 的位置。读者必须在登记后、读操作前 V(w)；若写成读完才 V(w)，读者全程占闸，其他读者连登记都做不了，读读并发荡然无存，退化成大锁。② 把 count 当信号量。count 是普通整型变量，靠 mutex 保护、靠 ++/-- 修改；对信号量只能 P/V、不能 ++/--。另：读者退出段的 count-- 同样要 P(mutex) 保护，常有人只保护进入段。

板书对照。讲义公平版旁白称其为「写者优先」，正文称「公平版」：从代码看，写者只是不再被后来读者插队、与读者按到达顺序过闸，并非后来读者必须让已在排队的写者绝对优先到「写者先于一切」的程度——称公平版更准确，实现与板书代码一致。读者优先版与反例中间版均与讲义推导过程一致。

六、三线程读写全局复数变量 综合题 · 8 分

题目。某进程中有 3 个并发执行的线程 thread1、thread2 和 thread3，其伪代码如下所示。请添加必要的信号量和 P、V（或 wait()、signal()）操作，要求确保线程互斥访问临界资源，并且最大限度地并发执行。

// 复数的结构类型定义
typedef struct {
float a;
float b;
} cnum;
cnum x, y, z; // 全局变量

// 计算两个复数之和
cnum add(cnum p, cnum q) {
cnum s;
s.a = p.a + q.a;
s.b = p.b + q.b;
return s;
}

thread1 {
cnum w;
w = add(x, y);
...
}

thread2 {
cnum w;
w = add(y, z);
...
}

thread3 {
cnum w;
w.a = 1;
w.b = 1;
z = add(z, w);
y = add(y, w);
...
}

分析：逐个变量拆读写关系

这道题是读者–写者模型的实战：不要整体看三个线程，先把每个变量的访问者名单列出来——谁读它、谁写它。判断一个变量要不要设防，只看一件事：有没有写者，以及写者之外还有谁。

w：三个线程各有一份，是局部变量，天然不共享——不设防。题面把 add 的参数、返回值都设计成按值传递，w 的赋值互不干扰。
x：只有 thread1 在 add(x, y) 里读它，全卷没有任何线程写 x。只读不写的数据永远读到的都是同一个值，不存在不一致——不设防。给 x 加锁纯属浪费，还白白降低并发。
y：thread1 读（add(x, y)）、thread2 读（add(y, z)）、thread3 既读又写（y = add(y, w)，先读 y 再写回 y）。读者两名（T1、T2），写者一名（T3）——对 y 完整套读者–写者模型：countY 记正在读 y 的线程数，mutexY 护 countY，rwY 实现「读者整体与写者互斥」。T1、T2 同读 y 时必须能并发，「最大限度并发」就卡在这里，用一把普通互斥锁锁 y 会把两个读串行化，不合格。
z：thread2 读（add(y, z)）、thread3 既读又写（z = add(z, w)）。写者仍是 T3，但读者只有 T2 一名——读读并发在这条变量上根本不存在，读者–写者模型里「第一个/最后一个读者」永远是同一个人，count 机制纯属空转。对 z 只需一把互斥锁 mutexZ：T2 读 z 时占着，T3 写 z 时占着，互斥关系就完整了。
粒度：保护只包住真正访问共享变量的语句。T3 的两次写（先 z 后 y，顺序按题面原样）是两个独立语句，题面没有要求「两次写原子完成」，所以不设一把大锁把 T3 整体包住——大锁会让 T3 写 z 时也挡住 T1 读 y，平白损失并发。T1、T2 代码里的「...」部分不访问 x、y、z，全部留在锁外。

信号量设计

名称初值管什么
rwY1y 的「读者整体（T1、T2）」与写者 T3 互斥
mutexY1保护整型变量 countY
countY（整型变量）0当前正在读 y 的线程数
mutexZ1z 的互斥访问（T2 读与 T3 写互斥；z 的读者只有一人，无需计数）

x、w 不设任何信号量，理由见分析。

代码

semaphore rwY = 1, mutexY = 1; // y 的读者-写者机制
semaphore mutexZ = 1; // z 的互斥锁

验算走查

走查一（并发有没有保住）。T1、T2 同时读 y：countY 到 2，rwY 由第一个读者占住，两人真并发。此时 T2 还要读 z，去 P(mutexZ)：z 无人写，立刻拿到，add(y, z) 完成。T1 全程不碰 z，T3 写 z 只等 mutexZ、写 y 只等 rwY——各等各的，互不牵连。

走查二（死锁排查，本题最危险处）。表面上 T2 在 add 期间同时占着「y 的读者身份」和 mutexZ，像是持锁等锁，细查不成环：其一，T3 写 z 时全程只持 mutexZ 一把锁，做完立刻释放，它持锁期间不等待任何其他锁，所以 T2 等 mutexZ 必有尽头；其二，T2 登记为 y 的读者时若 countY == 0，要 P(rwY)，此刻它可能持着 mutexY 等 rwY（T3 正在写 y），后来读者会排在 mutexY 上——但 T3 写 y 时不等待任何锁，写完必 V(rwY)，链条随之解开；其三，T3 的顺序是先 z 后 y 且写完 z 先放锁，不存在「持 z 等 y」与「持 y 等 z」的交叉持有。三个方向都封死，不成环。此方案经交错探索验算（三线程各执行一轮）：678 个可达状态，无写读冲突、无死锁。

易错点

① 给 x 也设一把锁。x 没有写者，加锁不解决任何问题，还可能把本可并发的读串行化，违背「最大限度并发」。② 对 z 也套完整读者–写者。z 的读者只有一个线程，count 机制空转，还平白多出一处要保护的计数竞态；判断用互斥还是读者–写者，看的是读者的数量，不看变量的长相。另：T3 两条写语句不要用一把大锁包圆（见分析粒度段）。

板书对照。讲义对本题只给出切入点：用读者–写者模型看，x 只被读不被写、T3 是 y 与 z 的写者，并点明对 y、z 分别设信号量——正文与此方向一致。其中 z 只设一把互斥锁、不套完整读者–写者机制，是正文按「z 的读者仅 T2 一人」收紧的，比泛泛「分别设信号量」更贴「最大限度并发」的要求。

七、哲学家进餐问题（模型题）

题目。有五个哲学家共用一张圆桌，分别坐在周围的五张椅子上，圆桌上有五只筷子（每两位哲学家之间一根）。他们的生活方式是交替地思考和进餐：饥饿时试图取左右最靠近他的筷子，只有拿到两根筷子时才能进餐，进餐完毕放下筷子继续思考。请用信号量机制描述哲学家的同步与互斥，并避免死锁。

本题研究的本质是：一个进程需要同时占有多个资源才能继续执行时，应该如何设计资源申请策略。

先给朴素解，并推演它为什么死锁

每根筷子是一件互斥资源：chopsticks[5]，初值各 1。最自然的写法是每位哲学家先拿左筷、再拿右筷：

semaphore chopsticks[5] = {1, 1, 1, 1, 1};

philosopher_i() { // 朴素解，会死锁
while (1) {
P(chopsticks[i]); // 拿左筷
P(chopsticks[(i + 1) % 5]); // 拿右筷
进餐;
V(chopsticks[i]);
V(chopsticks[(i + 1) % 5]);
思考;
}
}

死锁推演。设五人同时饥饿、同时被调度：五人各执行第一步 P(左筷) 全部成功——五根筷子各被一只手拿走（chopsticks 全为 0），每人手里一根。接着五人各执行 P(右筷)：右筷正是右邻的左筷，已在右邻手里，五人全部睡下。对照死锁四个必要条件：筷子互斥使用 ✓；筷子不可剥夺（不能从别人手里抢）✓；每人请求并保持（拿着一根等另一根）✓；五人的等待关系首尾相接成循环等待 ✓。四条全中，无人能再向前一步，也永远不会有人 V——死锁。（交错探索验算核对：朴素解的状态空间里确实存在死锁状态。）三种正解就是分别拆掉其中一条或几条。

方法 1：限人数——最多 4 人同时参与竞争

加一个计数信号量 count = n − 1 = 4，管「上桌抢筷子的名额」：先 P(count) 拿到名额才许伸手，名额满时第 5 人连第一根筷子都碰不到。

semaphore count = 4; // n-1，限制同时参与竞争的人数
semaphore chopsticks[5] = {1, 1, 1, 1, 1};

philosopher_i() {
while (1) {
P(count); // 先占一个竞争名额
P(chopsticks[i]);
P(chopsticks[(i + 1) % 5]);
进餐;
V(chopsticks[i]);
V(chopsticks[(i + 1) % 5]);
V(count);
思考;
}
}

为什么不死锁：至多 4 人参与竞争。若 4 人各持一根筷子，共用去 4 根，还剩 1 根空筷；这根空筷必定是某个持筷者的右筷（每根筷子都是某人的右筷），那个人就能拿起第二根吃上饭，吃完连放两根，等待链随之滚动。闭环需要 5 个人人手里一根、互相等——人数上限 4 让这个局面凑不齐。破坏的是循环等待（的形成条件）。此方案经交错探索验算：393393 个可达状态，无死锁。

方法 2：互斥取筷——用一把锁把取筷过程串行化

加互斥信号量 mutex = 1，把「拿左筷 + 拿右筷」这一串动作整体串行化：取筷期间只许一个人动手，拿齐两根才放行下一个人来取。

semaphore chopsticks[5] = {1, 1, 1, 1, 1};
semaphore mutex = 1; // 串行化「取双筷」这个动作

philosopher_i() {
while (1) {
P(mutex); // 开始取筷：期间别人不许取
P(chopsticks[i]);
P(chopsticks[(i + 1) % 5]);
V(mutex); // 取齐了，立刻放行别人取筷
进餐; // 进餐本身可以多人并发
V(chopsticks[i]);
V(chopsticks[(i + 1) % 5]);
思考;
}
}

为什么不死锁：先纠正一个容易想当然的说法——「持有一根、等第二根」的状态在本方法里照样存在：某位哲学家完全可能在 mutex 之内已拿起第一根、却卡在第二根上（第二根正被邻座用于进餐）。真正让它不死锁的是两点合起来：其一，取筷阶段被 mutex 串行化，同一时刻至多一个人处于「持一等二」，其余想取筷的人全被挡在 mutex 之外、两手空空；其二，正在进餐的人不等待任何筷子（已经拿齐了），必然能吃完并把筷子放下。于是那位「持一等二」者等的筷子终将被进餐者释放，他能拿齐、吃完、放下，mutex 随之轮转给下一个人——等待关系或许经 mutex 串成几节（后到者等 mutex、持筷者等筷子），但至多一人持筷等待、其余等待者两手空空，链条最终指向一位不等待任何人的进餐者，循环等待根本形不成。破坏的是循环等待，不是请求并保持（持一等二依然存在，只是被限制到至多一人）。

方法 3：奇偶分序——改掉统一的申请顺序

不加任何新信号量，只改拿筷的先后：编号为奇数的哲学家先左后右，偶数的先右后左（编号 0～4）。

semaphore chopsticks[5] = {1, 1, 1, 1, 1};

philosopher_i() {
while (1) {
if (i % 2 == 1) { // 奇数位：先左后右
P(chopsticks[i]);
P(chopsticks[(i + 1) % 5]);
} else { // 偶数位：先右后左
P(chopsticks[(i + 1) % 5]);
P(chopsticks[i]);
}
进餐;
V(chopsticks[i]);
V(chopsticks[(i + 1) % 5]);
思考;
}
}

为什么不死锁：循环等待能成环，前提是所有人按同一个方向申请（人人先左后右，等待箭头才能首尾相接）。奇偶分序后，相邻两人对他俩中间那根筷子的争夺方向相反：中间筷若是奇数位的左筷，就是偶数位的右筷，两人都是「先拿它」——这根筷子被谁先拿走，另一人两手空空地等，不持有任何筷子，等待箭头到此断掉，环结不起来。具体看一根：0 号（偶数位，先右后左）与 1 号（奇数位，先左后右）第一根要抢的都是 chopsticks[1]，不可能同时各持第一根；而全环的循环等待要求人人持一等一，这个局面凑不齐，故环不能形成。破坏的是循环等待。此方案经交错探索验算：49409 个可达状态，无死锁。

① 方法 1 的 count 初值写成 5 或 n。等于没限，死锁照旧；初值必须是 n − 1，且这个数随人数变，不是写死的 4。② 把两个 count 混为一谈。本节的 count 是信号量（只能 P/V）；读者–写者里的 count 是整型变量（可以 ++/--、要 mutex 保护）。同名不同物，考试写错类型直接判错。

八、哲学家加碗变种 综合题 · 8 分

题目。有 n（n ≥ 3）位哲学家围坐在一张圆桌边，每位哲学家交替地就餐和思考。在圆桌中心有 m（m ≥ 1）个碗，每两位哲学家之间有一根筷子。每位哲学家必须取到一个碗和两侧的筷子后，才能就餐；进餐完毕，将碗和筷子放回原位，并继续思考。为使尽可能多的哲学家同时就餐，且防止出现死锁现象，请使用信号量的 P、V 操作［wait()、signal() 操作］描述上述过程中的互斥与同步，并说明所用信号量及初值的含义。

分析：拆约束

在哲学家基本题之上只多了一样东西：碗。但「取到碗」和「防死锁」这两件事，最后落在同一个数字上——先把这个数字管的对象说准：count 限制的是参与取筷竞争的人数，不是「同时就餐的人数」。拆开看，竞争人数被两条上限卡着：
其一，碗数限制 m：参与竞争的人先占一个碗（没分到碗的人不进入取筷竞争），竞争人数不可能超过碗数，这是资源计数约束。
其二，防死锁竞争限制 n − 1：方法 1 的结论——在人人统一「先左后右」的申请策略下，参与竞争的人数只要达到 n，就可能凑出人手一根筷子的循环等待；压到 n − 1 以内，死锁不可能发生。所以 n − 1 是「统一先左后右策略下、允许参与取筷竞争的安全人数限制」。
特别点明：n − 1 不是同时就餐人数的上限。物理上同时就餐人数另有上限：相邻两人不能同吃（共用一根筷子），n 人围桌至多 ⌊n/2⌋ 人同时进餐，再叠加碗数，同时就餐上限 ＝ min{m, ⌊n/2⌋}——这个数由圆桌与碗的实物格局自然决定，不需要信号量去管；信号量要管的是竞争准入。题目要求「尽可能多同时就餐」且「防止死锁」，落到竞争人数上就是两个限制同时满足、取其小：count = min{m, n − 1}，即碗数限制与防死锁竞争限制取小。分情况看：m < n − 1 时碗是瓶颈，count = m，竞争人数被碗卡住、天然也在防死锁线以内；m ≥ n − 1 时碗够用，count = n − 1，瓶颈换成防死锁线，多一个碗也不多放一个人进来竞争。
实现上沿用方法 1 的框架，只设这一个 count，不再为碗单设信号量：因为「进场参与竞争」与「占用一个碗」在本题里是绑定的同一个动作——P(count) 成功，即同时意味着「有名额」和「有碗」。把两者分设两个信号量（进场 n − 1、碗 m）效果完全等价，只是多一个量、多一处 P/V；合并成一个初值取 min 的 count，是信号量最少、又恰好落实双上限的写法。筷子则按 n 人泛化：chopstick[n]，初值各 1，右筷为 (i + 1) % n。

验算走查

走查（n = 5、m = 2 的小碗情形）。count = min{2, 4} = 2：最多 2 人上桌竞争，每人必有碗（在座 ≤ 2 = 碗数）。死锁方面，在座人数 2 < 5，就算两人都各持一根筷子，桌上还剩 3 根空筷，其中必有一根是某人的右筷，他能吃完并释放——方法 1 的论证原样成立。再看 m = 6、n = 5：count = min{6, 4} = 4，碗多出来 2 个闲置，但竞争人数仍被 4 卡住——此时 6 个碗、5 位哲学家，人人都有碗可拿；若只按碗数限制竞争（count 错设成 6 乃至 5），5 人就可能全员参与取筷竞争，各自先拿左筷、再等右筷，形成循环等待。因此仍需把竞争名额限制在 n−1 以内——双上限取小，卡的正是这种情形。

易错点

① count 只取 n − 1、忘了与 m 比较。这是本题的命题眼：m 比 n − 1 小时，count = n − 1 会放进来比碗多的人，无碗者占着筷子干等，轻则浪费、重则与持碗者互相牵制。② 为碗单设信号量又忘了防死锁。只设 bowl = m 而不限人数，m ≥ n 时死锁原样复活——碗要管，人数也要管，合并成 min 一步到位。

板书对照。老师手写板书沿用了基本题 5 人情形的写法：只写 count = n − 1，筷子数组仍写 chopstick[5]、取模仍是 %5，且未在板书上落实碗的约束——板书是顺手套用方法 1 的痕迹。正文按题面 n 人、m 碗的一般情形改：筷子数组泛化为 [n]、取模 %n，count 初值落实为老师在讲解中给出的结论 min{m, n − 1}。

九、单缓冲区 B 的同步互斥 综合题 · 8 分

题目。计算机系统中的进程之间往往需要相互协作以完成一个任务。在某网络系统中，缓冲区 B 用于存放一个数据分组，对 B 的操作有 C1、C2 和 C3。C1 将一个数据分组写入 B 中，C2 从 B 中读出一个数据分组，C3 对 B 中的数据分组进行修改。要求 B 为空时才能执行 C1，B 非空时才能执行 C2 和 C3。请回答下列问题。

(1) 假设进程 P1 和 P2 均需要执行 C1，实现 C1 的代码是否为临界区？为什么？（2 分）

(2) 假设 B 初始为空，进程 P1 执行 C1 一次，进程 P2 执行 C2 一次。请定义尽可能少的信号量，并用 wait()、signal() 操作描述进程 P1 和 P2 之间的同步或互斥关系，说明所用信号量的作用及其初值。（3 分）

(3) 假设 B 初始不为空，进程 P1 和 P2 各执行 C3 一次。请定义尽可能少的信号量，并用 wait()、signal() 操作描述进程 P1 和 P2 之间的同步或互斥关系，说明所用信号量的作用及其初值。（3 分）

第 (1) 问：C1 是不是临界区

答：是临界区。判断分两步。第一步看 B 是不是临界资源：临界资源指一次仅允许一个进程使用的资源。B 同一时刻只能存放一个数据分组，C1 是往 B 里写分组的操作；若 P1、P2 并发执行 C1，两个分组的写入会互相覆盖、交错，把 B 中的内容写坏——所以 B 只能被独占使用，是临界资源。第二步套定义：临界区指进程中访问临界资源的那段代码。实现 C1 的代码正是访问 B 的代码段，所以它就是临界区，必须互斥执行。（注意：结论与「B 此刻空不空」无关——空与非空管的是 C1 能不能执行，临界区管的是执行时能不能并发，两回事。）

第 (2) 问：B 初空，P1 写一次、P2 读一次

分析。把约束摊开：互斥？读写不能并发——但在这个场景里它被同步自动解决了，见下。同步，一条：C2 必须在 C1 之后（B 初始为空，没写之前无物可读）。计数？B 只能放一个分组，但 P1 总共只写一次，「B 已满还要写」的情形不存在，不需要管空位的信号量。
为什么连 mutex 都可以省：两个进程各执行一次。给唯一的同步条件配上信号量后，P2 在信号量上睡到 P1 写完才开始读——读和写在时间上被彻底错开，不存在任何「同时访问 B」的窗口，互斥没有用武之地。这就是「尽可能少」的着力点：同步量 1 个，多一个都是多余。

S0同步信号量：表示「B 中已有可读分组」这一条件是否成立。P1 写毕 signal，P2 读前 wait

走查。P2 先被调度：wait(S)，S = 0，睡下，碰不到 B。P1 执行 C1 写完，signal(S)：若 P2 在等，唤醒它读；若 P1 先跑完、无人等待，S 记为 1，P2 后来 wait(S) 直接通过——「写完过」这个事件被计数保住了，不会丢。再确认不需要第二个信号量：B 从空变非空只发生一次（P1 只写一次），P2 读走之后没人再写、没人再读，故事结束。此问经交错探索验算：C2 的断言「执行时 B 必已写入」在所有交错下成立，无死锁。

第 (3) 问：B 初非空，两进程各执行一次 C3

分析。前提反转，约束也跟着反转。同步？C3 的执行条件是「B 非空」，初始 B 就非空，两次 C3 之间题目没有规定任何先后——同步量无事可做，一个都不设。计数？不涉及。互斥？这回成为唯一的、也是必须的约束：C3 是「读出—修改—写回」的复合操作，若两进程交错执行，会丢修改（见走查），所以 C3 整体必须互斥，一把 mutex 足矣。

① 第 (2) 问照搬模板凑信号量。把 empty、full、mutex 一套三件搬上来，每个都不算「错」，但题目明说「尽可能少」——多设的每一个都是扣分点。本问的功力全在敢于只留一个。② 第 (3) 问误加同步量。比如设个 S = 0 让 P2 等 P1 先做完：题目没规定顺序，加了是画蛇添足；更危险的是若代码里没人 signal，P2 直接死等，从对的写成错的。第 (2)、(3) 问正好是一对镜像：一个只要同步不要互斥，一个只要互斥不要同步，先把约束种类认准再动手。

十、三人植树流水线 综合题 · 8 分

题目。三个人一起植树，甲挖坑，乙放树苗入坑并填土，丙负责为新种树苗浇水。步骤依次为：挖树坑、放树苗、填土和浇水。现有铁锹和水桶各一个，铁锹用于挖树坑和填土，水桶用于浇水。当树坑数量小于 3 时，甲才可以挖树坑。设初始坑数为 0，铁锹、水桶均可用。定义尽可能少的信号量，用 wait() 和 signal() 操作描述植树过程中三人的同步互斥关系，并说明所用信号量的作用及其初值。

分析：拆约束

先把分工钉死：甲只做挖坑；乙一个人做放树苗和填土两步（题面是三个人，不是四个人）；丙只做浇水。四步构成一条流水线：挖坑 → 放树苗 → 填土 → 浇水，循环往复。
同步，两条链：挖好的坑才能放苗——dug，记「已挖好、待放苗的坑数」；填好土才能浇水——filled，记「已填土、待浇水的坑数」。两者初值都是 0（初始坑数为 0，上游没产出之前下游只能等）。注意四步之间的三条边只有这两条需要信号量：「放树苗 → 填土」这一边不设信号量——这两步同是乙一个人的相邻动作，乙的程序顺序（先写放苗、后写填土）本身就保证了先后，一个进程与自己之间不存在需要同步的并发。若给它配一个 planted，让乙放苗后 signal、填土前又 wait，就是乙自己给自己发通知再自己接收，纯属冗余，是一个只有乙自己 signal 又 wait 的量，违背题面「尽可能少」——同步信号量只配给真正跨进程的等待。
互斥，一条：铁锹只有一把，甲挖坑与乙填土都要用——shovel = 1。水桶也只有一个，但只有丙一个人用：互斥的前提是「有人争」，没人争的东西设信号量纯属多余，同样违背「尽可能少」——水桶不设信号量，丙拿起来就用。
资源计数，一条：树坑数量小于 3 时甲才能挖。先把「树坑数量」的口径定准：hole 管的是尚未完成填土的树坑任务数——一个坑一旦填完土，它作为「树坑」的任务就结束了；剩下的浇水是对已成型新树苗的养护，积压多少都不再占用树坑名额。名额信号量 hole = 3：甲挖坑前 wait(hole) 先预约一个名额，乙填完土时 signal(hole) 归还。归还为什么放在乙填土后、而不是丙浇水后，用一个反例最能说明：设 3 个坑全已填好土、正排队等丙浇水，此刻尚未完成填土的坑实际是 0 个；若名额要等浇水后才还，hole 仍是 0，甲会被白白挡住——这等于把浇水环节的积压也算进了树坑容量，与题面「树坑数量小于 3」的口径不符。浇水慢只该让丙自己忙，不该堵住甲挖新坑。反过来，名额也不能由甲挖完后自己归还，那等于不设限。再看甲的动作次序：wait(hole) 排在 wait(shovel) 之前，甲可能先占下名额、再去等铁锹——这是计数信号量的预留机制：名额是对「将要挖的坑」的配额预约，先预约、后施工，配额计数（未填土坑数）不会因为等铁锹而失真，这个次序没有问题。

验算走查

走查一（铁锹争用与名额预留）。甲正要挖第 2 个坑，乙正用铁锹填第 1 个坑的土：甲先 wait(hole) 占下第 2 个名额，再 wait(shovel) 睡下。注意此时甲「持有」的只是一个名额——名额不是锁，占着它不妨碍任何人推进，乙填完土 signal(shovel)，甲被唤醒续挖；乙随后 signal(hole)，把第 1 个坑的名额还掉。再看反方向：乙填土前 wait(shovel) 被甲的挖坑挡住时，乙同样不持有任何锁（dug 已消费完、还没碰锹）。两边都不持锁等锁，锹的当前使用者做完必还，不成环。

走查二（上限口径与源头限流）。甲手快、乙手慢（还没填任何一个坑）：甲连挖 3 坑，hole 3 → 0，第 4 次 wait(hole) 睡下——哪怕铁锹空着、dug 已经攒了 3，也不许再挖，未完成填土的坑数被牢牢卡在 3 以内。乙每填完一个坑 signal(hole) 一次，甲才被放行一个。再验归还时机的口径：3 个坑全部填完土、正排队等丙浇水时，hole 已经回到 3，甲可以继续挖新坑——浇水环节的积压不占树坑名额，这正是把归还放在填土之后的效果；若错放在浇水之后，此刻 hole 仍是 0，甲会被浇水积压白白堵住。此方案经交错探索验算（三人各 3 轮）：铁锹从未被两人同时持有、未完成填土的坑数从未超过 3、步骤次序断言全过、无死锁。

易错点

① 把乙拆成两个进程。「放苗进程 + 填土进程」是四个人，与题面三人分工不符；乙的两步必须写在同一个进程里一前一后。② 给水桶也设信号量。单人使用的资源不设防，这是「尽可能少」的常见考点；与之对称，铁锹是两人共用，只给甲或只给乙上锁都算漏互斥。③ hole 的 signal 位置。放在丙浇水后归还，会把浇水积压算进树坑容量，上限口径错位（见分析反例）；放在甲自己挖完后归还，则名额形同虚设。正解是乙填土后归还。④ 给乙自己的相邻两步配 planted 信号量。放苗后 signal、填土前 wait，接收者还是乙自己——同步量只配跨进程的边，这种自发自收的量是纯冗余，同样违背「尽可能少」。

板书对照。讲义板书只有分工拆解（甲挖坑；乙放树苗、填土；丙浇水）与正文一致，信号量未在讲义中给出；旁白提到的「坑位/名额」信号量即正文的 hole。讲义另提醒避免用共享变量加额外互斥锁的写法（容易盲等又增加信号量个数），正文全程用信号量表达同步、未引入共享计数变量，与该口径一致。
